# Architecture Plan Template

The template for every plan file `code-architect` writes. Multi-step build formats (`Build
Steps`, session docs) are in [multistep.md](multistep.md).

**A plan file written to a committed repo path** (`docs/design.md`, `docs/sessions/*`,
`docs/plans/*`) starts with the line `<!-- markdownlint-disable MD013 MD025 MD040 MD041 -->`,
placed immediately after the YAML frontmatter when the file has one, otherwise as the first line.
Repos gate committed docs with markdownlint in pre-commit, and plan formatting violates those four
rules. Plans in `claude-work/` are transient and skip it.

---

## Template

```markdown
# Architecture Plan: [Feature/Problem Name]

_Generated by code-architect. This is a living document — it should be updated when the plan changes OR when implementation reveals the plan was wrong._

## Problem Statement
[Restate the problem in your own words, including key constraints and requirements as understood.]

## Assumptions
[List every assumption made. These are the things that could break the design if wrong. Remove or correct entries as they are validated or disproven during implementation.]

## Input / Output States

Define every distinct input state the system may encounter, every terminal output state it can produce, and which input maps to which output. This is the contract — write it before anything else.

**Input states:** every meaningful condition of the inputs (presence/absence of a file, value of a config flag, content of a tag, etc.). Cover the happy path AND the failure / edge conditions.

**Output states:** every terminal state the system can end in (success with side effect X, success with side effect Y, failure with code N, no-op, etc.). Include exit codes, tags written, files produced, metadata changes — anything observable from outside.

**Mapping:** for each input state, which output state it leads to and why. A state with no mapping is a bug in the plan.

| Input state | Output state | Notes |
|---|---|---|
| [e.g., DICOM file present, tag X = "approved"] | [e.g., success, adds tag "auto-approved"] | [Why / what happens in between] |
| [e.g., DICOM file present, tag X missing] | [e.g., success, adds tag "needs-review"] | |
| [e.g., input file corrupted] | [e.g., failure, exit code 1, logs error] | |

If two input states map to the same output, list them as separate rows — do not collapse. If an input state is "impossible by construction," still list it and say so.

## Design Rationale

Every reason names something about this problem. "Strategy improves extensibility" is not a
reason; "three export targets share a skeleton and differ only in the write step" is.

**Pattern:** [Name, or "plain functions" for small work with no variation point]
- **Why:** [What about this problem the pattern fits — the specific reasons]
- **Rejected:** [The close contender, if there was one, and why it lost]

**Workflow:** [The N main parts the work splits into, one line each]
- **Why this split:** [What each split buys — a test seam, a swap point, a boundary around an
  external system — and why it isn't fewer or more parts]

**Key decisions:** [One entry per decision: the choice, why, and what it beat]
```

```
  - `method_name` — [Same]

[Repeat for each module]

1. [Step]

## Tasks

Ordered, independently implementable tasks. Each task must be small enough to verify on its own, ordered by dependency, and leave the codebase in a working state when complete. The PM hands the task list to code-writer, which implements and verifies the tasks in order. A plan without a task list cannot be executed — it can only be admired.

### Task 1 — [name]
- **Files:** [files created or modified by this task]
- **Behavior:** [plain-language spec of what exists after this task that didn't before — unambiguous, no code]
- **Verify:** [exact command to run and what output proves the task is done, e.g. `uv run pytest tests/test_loader.py` exits 0]

### Task 2 — [name]
[Repeat for each task]

## Risks & Trade-offs
- [Risk or trade-off]: [Why it exists, what to watch for]

## Open Questions
[Anything unresolved that could affect the design. Remove items as they are resolved.]

## Revision History
[Date] — [What changed and why]
```
