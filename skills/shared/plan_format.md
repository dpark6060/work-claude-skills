# Architecture Plan Format

This is the canonical template for architecture plan files produced by the `code-architect` and `change-planner` skills and consumed by the `code-architect-reviewer` skill. All three must treat this as the source of truth.

---

## Template

```markdown
# Architecture Plan: [Feature/Problem Name]

_Generated by code-architect. This is a living document — it should be updated when the plan changes OR when implementation reveals the plan was wrong._

## Problem Statement
[Restate the problem in your own words, including key constraints and requirements as understood.]

## Assumptions
[List every assumption made. These are the things that could break the design if wrong. Remove or correct entries as they are validated or disproven during implementation.]

## Input / Output States

Define every distinct input state the system may encounter, every terminal output state it can produce, and which input maps to which output. This is the contract — write it before anything else.

**Input states:** every meaningful condition of the inputs (presence/absence of a file, value of a config flag, content of a tag, etc.). Cover the happy path AND the failure / edge conditions.

**Output states:** every terminal state the system can end in (success with side effect X, success with side effect Y, failure with code N, no-op, etc.). Include exit codes, tags written, files produced, metadata changes — anything observable from outside.

**Mapping:** for each input state, which output state it leads to and why. A state with no mapping is a bug in the plan.

| Input state | Output state | Notes |
|---|---|---|
| [e.g., DICOM file present, tag X = "approved"] | [e.g., success, adds tag "auto-approved"] | [Why / what happens in between] |
| [e.g., DICOM file present, tag X missing] | [e.g., success, adds tag "needs-review"] | |
| [e.g., input file corrupted] | [e.g., failure, exit code 1, logs error] | |

If two input states map to the same output, list them as separate rows — do not collapse. If an input state is "impossible by construction," still list it and say so.

## Design Decision
**Pattern chosen:** [Name]
**Rationale:** [Why this pattern fits this problem]
**Rejected alternatives:** [What else was considered and why it was ruled out]

## Module Map

```
project/
├── file_a.py     # [One-sentence responsibility]
├── file_b.py     # [One-sentence responsibility]
└── file_c.py     # [One-sentence responsibility]
```

### [file_a.py]
- **Owns:** [What data, logic, or I/O this module is responsible for]
- **Does NOT own:** [Explicit exclusions to prevent responsibility creep]
- **Key methods/functions (broad):**
  - `method_name` — [What it does, what data it receives, what it returns or passes on]
  - `method_name` — [Same]

### [file_b.py]
[Repeat for each module]

## Data Flow

[Describe the end-to-end path data takes through the system in numbered steps. Be specific about the form data is in at each handoff — e.g., "raw dict", "validated dataclass", "list of result objects". Do not write method signatures; describe intent.]

1. [Step]
2. [Step]
3. [Step]

## Tasks

Ordered, independently implementable tasks. Each task must be small enough to verify on its own, ordered by dependency, and leave the codebase in a working state when complete. The PM dispatches one code-writer per task, in order. A plan without a task list cannot be executed — it can only be admired.

### Task 1 — [name]
- **Files:** [files created or modified by this task]
- **Behavior:** [plain-language spec of what exists after this task that didn't before — unambiguous, no code]
- **Verify:** [exact command to run and what output proves the task is done, e.g. `uv run pytest tests/test_loader.py` exits 0]

### Task 2 — [name]
[Repeat for each task]

## Risks & Trade-offs
- [Risk or trade-off]: [Why it exists, what to watch for]

## Open Questions
[Anything unresolved that could affect the design. Remove items as they are resolved.]

## Revision History
[Date] — [What changed and why]
```

## Multi-step builds

A project delivered as several steps — one conversation and one MR each — replaces the `Tasks` section with `Build Steps`, and puts the per-step detail in its own session doc written just before that step starts. See the Modes section of the `code-architect` skill for which mode writes what.

`docs/design.md` keeps everything above the depth line: Input → Output mapping, module map, cross-boundary data contracts, decisions, risks. Per-step entries stay shallow:

```markdown
## Build Steps

Ordered. Only the `NEXT` step has a session doc; the rest are deliberately shallow and
are expected to change as earlier steps teach us things.

### Step 2 — Archive db + PHI gate
Status: NEXT
Purpose: one or two sentences.
- bullet
- bullet

### Step 3 — File discovery
Status: OUTLINE
Purpose: one or two sentences.
- bullet

### Step 1 — Scaffolding + models
Status: DONE (MR !8)
Learned: ImageRef.FileSize is the exact sum of all files for a basename, not
  approximate — the byte check is now exact. Real schema is 21 tables and 37
  ImageRef columns, not 5 and 12.
```

Status vocabulary: `OUTLINE`, `NEXT`, `DONE (MR !N)`. Exactly one step is `NEXT` at a time; `NEXT` covers both "detailed, not started" and "in progress", distinguished by whether its session doc exists. `Learned` appears only on `DONE` steps and only `reconcile` writes it — in the same pass that promotes the next step to `NEXT`, so the two cannot drift.

### Session doc template

Written by `detail <N>` to `docs/sessions/session-0N-<slug>.md`. This is where full depth belongs — signatures, behavior rules, error strings, test requirements. Completed session docs are kept as the code-level record of what was actually built, and later steps read the most recent ones.

```markdown
---
title: Session N — [name]
description: [one line, for docs/sessions/index.md]
---

## Context
[Why this step exists, what it depends on, what shipped before it.]

## Read first
[Specific files and sections — design.md sections, prior session docs, real code.]

## Module surfaces
[Per module: signatures with behavior comments. Full depth.]

## Behavior rules
[Ordering, edge cases, error handling, exact strings where they are contractual.]

## Testing requirements
[Concrete cases, including the regression tests for anything a prior step got wrong.]

## Tasks
[The dispatchable `Tasks` section above. This is what makes the step executable.]

## Out of scope
[What belongs to a later step. Prevents scope creep into unstarted work.]
```

## Reviewer Verdicts

When the `code-architect-reviewer` evaluates code against a plan, it assigns one of these verdicts per file:

| Verdict | Meaning |
|---|---|
| `Matches Plan` | Code aligns with the plan's intent |
| `Deviates from Plan` | Code diverges in a way that matters — code should change |
| `Plan Was Wrong` | Code is correct, but the plan didn't anticipate this — plan should update |
| `Plan Needs Rethinking` | The plan's approach is causing real problems in practice — a design change is warranted |
