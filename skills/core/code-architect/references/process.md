# Mode: process

Map a workflow at the process level — the steps, the actors, the data that moves between them,
and the format each handoff takes. No code, classes, libraries, or file structure; that is
`design` mode's job, and it runs after this one. The deliverable is a validated mermaid diagram
plus the process decisions behind it.

## Mindset

- A step is something that happens, not a function. Each one has an actor or system that
  performs it.
- Every handoff carries the minimum data the next step needs, in a format chosen on purpose.
  "Some data gets passed" is not a decision.
- A diagram the team can read and debate beats a complete one nobody looks at.

## Questions

- **Actors and systems**: who or what is involved (humans, automated services, external
  systems, databases, queues)?
- **Trigger**: what starts the process — an event, a schedule, a human, another process?
- **Happy path**: the major phases in sequence.
- **Data that must survive handoffs**: what a later step needs from an earlier one, where it
  comes from, and where it must end up.
- **Failure and exception paths**: what can go wrong, and what happens then.
- **External systems**: what the process reads from or writes to outside itself.

## Design the workflow

**Map the steps.** For each step in order: what triggers it, what it does in plain language, and
what it produces or changes.

**Identify the data handoffs.** For each transition: what data must pass, the minimum needed,
and who consumes it for what.

**Decide each handoff's format**, with the reason it fits and the contender it beat:

| Format | Best when... |
|---|---|
| File on disk (CSV, JSON, text) | Steps run at different times, data needs to be auditable or human-readable |
| Metadata tag on a container | Data is tied to a specific object and consumed by downstream tools that read that object |
| Database record | Data is queried, filtered, or updated by multiple actors |
| In-memory / return value | Steps run in the same process with no persistence needed |
| Message / event | Steps are decoupled services that react asynchronously |
| Structured log entry | Data is observational — not consumed programmatically, but must be traceable |

**Pick the diagram type:**

- `flowchart TD` — sequential steps with decision branches; best for single-actor processes
- `sequenceDiagram` — multi-actor interactions over time; best when timing and message exchange
  matter
- `stateDiagram-v2` — system states and transitions; best for lifecycle or status-driven
  processes
- Use two diagrams if one type cannot capture both the flow and the actor interactions cleanly

**Flag risks:** steps where the process could stall, deadlock, or produce inconsistent state;
handoffs where the format is a real trade-off (a tag is convenient but not queryable); and
assumptions that break the design if wrong.

## Validate the diagram

Before presenting or saving, write each mermaid block to a temp file in the scratchpad and run
`mmdc -i diagram.mmd -o diagram.svg`. A non-zero exit means the syntax is invalid: fix it and
re-validate. A diagram that fails to render is worse than no diagram. This step runs with or
without a user.

## Present

1. The mermaid diagram(s)
2. A short summary of the handoff format decisions and their reasons
3. The flagged risks

## Process design file

Default path: `claude-work/code_architect/process-design.md`.

```markdown
# Process Design: [Process Name]

_Generated by code-architect (process mode). Update this file when the process changes or when
real-world implementation reveals the design was wrong._

## Process Summary
[2–3 sentences describing what this process does and why it exists.]

## Actors and Systems
[Each actor/system and its role in one sentence.]

## Process Steps
[Numbered list. For each: what triggers it, what it does, what it produces.]

## Data Handoffs

| From | To | Data | Format | Rationale |
|---|---|---|---|---|
| Step N | Step M | [What data] | [Format chosen] | [Why, and the contender it beat] |

## Mermaid Diagram

[Validated mermaid block(s)]

## Risks and Open Questions
[Anything unresolved, plus every assumption made without a user.]

## Revision History
[Date] — [What changed and why]
```
