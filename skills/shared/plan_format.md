# Architecture Plan Format

This is the canonical template for architecture plan files produced by the `architect_planner` skill and consumed by the `architect_reviewer` skill. Both skills must treat this as the source of truth.

---

## Template

```markdown
# Architecture Plan: [Feature/Problem Name]

_Generated by architect_planner. This is a living document — it should be updated when the plan changes OR when implementation reveals the plan was wrong._

## Problem Statement
[Restate the problem in your own words, including key constraints and requirements as understood.]

## Assumptions
[List every assumption made. These are the things that could break the design if wrong. Remove or correct entries as they are validated or disproven during implementation.]

## Input / Output States

Define every distinct input state the system may encounter, every terminal output state it can produce, and which input maps to which output. This is the contract — write it before anything else.

**Input states:** every meaningful condition of the inputs (presence/absence of a file, value of a config flag, content of a tag, etc.). Cover the happy path AND the failure / edge conditions.

**Output states:** every terminal state the system can end in (success with side effect X, success with side effect Y, failure with code N, no-op, etc.). Include exit codes, tags written, files produced, metadata changes — anything observable from outside.

**Mapping:** for each input state, which output state it leads to and why. A state with no mapping is a bug in the plan.

| Input state | Output state | Notes |
|---|---|---|
| [e.g., DICOM file present, tag X = "approved"] | [e.g., success, adds tag "auto-approved"] | [Why / what happens in between] |
| [e.g., DICOM file present, tag X missing] | [e.g., success, adds tag "needs-review"] | |
| [e.g., input file corrupted] | [e.g., failure, exit code 1, logs error] | |

If two input states map to the same output, list them as separate rows — do not collapse. If an input state is "impossible by construction," still list it and say so.

## Design Decision
**Pattern chosen:** [Name]
**Rationale:** [Why this pattern fits this problem]
**Rejected alternatives:** [What else was considered and why it was ruled out]

## Module Map

```
project/
├── file_a.py     # [One-sentence responsibility]
├── file_b.py     # [One-sentence responsibility]
└── file_c.py     # [One-sentence responsibility]
```

### [file_a.py]
- **Owns:** [What data, logic, or I/O this module is responsible for]
- **Does NOT own:** [Explicit exclusions to prevent responsibility creep]
- **Key methods/functions (broad):**
  - `method_name` — [What it does, what data it receives, what it returns or passes on]
  - `method_name` — [Same]

### [file_b.py]
[Repeat for each module]

## Data Flow

[Describe the end-to-end path data takes through the system in numbered steps. Be specific about the form data is in at each handoff — e.g., "raw dict", "validated dataclass", "list of result objects". Do not write method signatures; describe intent.]

1. [Step]
2. [Step]
3. [Step]

## Risks & Trade-offs
- [Risk or trade-off]: [Why it exists, what to watch for]

## Open Questions
[Anything unresolved that could affect the design. Remove items as they are resolved.]

## Revision History
[Date] — [What changed and why]
```

## Reviewer Verdicts

When the `architect_reviewer` evaluates code against a plan, it assigns one of these verdicts per file:

| Verdict | Meaning |
|---|---|
| `Matches Plan` | Code aligns with the plan's intent |
| `Deviates from Plan` | Code diverges in a way that matters — code should change |
| `Plan Was Wrong` | Code is correct, but the plan didn't anticipate this — plan should update |
| `Plan Needs Rethinking` | The plan's approach is causing real problems in practice — a design change is warranted |
